import { useSwapExecution } from '@/lib/useSwapExecution';
import { TransactionConfirmation } from '@/components/TransactionConfirmation';

PART 2: WALLET AUTHENTICATION & SIGNING
================================================================================

Privy Embedded Wallet System

Tower Exchange uses Privy for both authentication and transaction signing.

AUTHENTICATION FLOW:

1. User lands on application
2. Privy login modal appears (email or social login)
3. Upon successful authentication, Privy creates or connects embedded wallet
4. User wallet address is available immediately
5. No additional setup required for wallet connection

WALLET FEATURES:

- Non-custodial: Users retain full private key control
- Embedded: Wallet UI seamlessly integrated into app
- Cross-chain: Supports multiple blockchain networks
- Multi-backup: Hardware wallet and recovery phrase support
- Session persistence: Authentication survives page refreshes
- Automatic signing: Privy handles pop-up UX for transaction approval

PART 3: SMART CONTRACT INTERACTION & RPC
================================================================================

JSON-RPC Integration with Arc Blockchain

Direct interaction with Arc testnet for transaction submission and confirmation.

ARC RPC ENDPOINT:
https://rpc.testnet.arc.network


Use this endpoint for all blockchain interactions. Implement request retries for
reliability and add exponential backoff for rate limiting.

SUPPORTED RPC METHODS:

eth_sendTransaction
  Purpose: Broadcast signed transaction to network
  Used for: Submitting swaps after user signs
  Return: Transaction hash (0xabc123...)

eth_getTransactionReceipt
  Purpose: Retrieve transaction confirmation details
  Used for: Polling transaction status until confirmed
  Return: Receipt with block number, gas used, status

eth_blockNumber
  Purpose: Get current block height
  Used for: Checking network sync status
  Return: Block number in hex format

eth_call
  Purpose: Execute view functions on contracts
  Used for: Reading token balances, checking allowances
  Return: Contract function output (no state change)

TRANSACTION POOLING LOGIC:

After user signs transaction, implement polling:

1. Start polling loop (every 1 second)
2. Call eth_getTransactionReceipt with transaction hash
3. Receipt is null if still pending (not in block yet)
4. Continue until receipt is received
5. Check receipt.status field (1 = success, 0 = failure)
6. Timeout if no receipt after 30 seconds
7. Return success/failure status to user

EXAMPLE REQUEST/RESPONSE:

POST request to Arc RPC:

{
  "jsonrpc": "2.0",
  "method": "eth_getTransactionReceipt",
  "params": ["0x1a2b3c..."],
  "id": 1
}

Response when confirmed:

{
  "jsonrpc": "2.0",
  "result": {
    "blockNumber": "0x12a4b5",
    "transactionHash": "0x1a2b3c...",
    "gasUsed": "0x23e5c",
    "status": "0x1"
  }
}

ROUTER CONTRACT INTEGRATION:

The DEX Router contract receives swap instructions via encoded function calls.

Transaction structure:
  to: DEX Router contract address
  data: ABI-encoded function call (generated by backend)
  value: "0" (no ETH required for token swaps)
  from: User wallet address
  gasLimit: "300000" (calculated by backend for specific swap)

Backend handles:
  - Token approval checking (if needed)
  - Optimal gas limit calculation
  - Slippage protection (minimum output amount)
  - Route optimization through multiple pools

Frontend only needs to pass these values to wallet.

REST API Endpoints for Chat and Transaction Management

All backend endpoints require authentication via API key header.

CHAT ENDPOINT

POST /api/v1/chat

Headers:
  Content-Type: application/json
  endpoint_auth: YOUR_API_KEY (for server-to-server calls)

Request Payload:
  
  message (string, required)
    User message to AI agent
    Example: "Swap 1 USDC to EURC"
    
  userid (string, required)
    Unique user identifier (wallet address)
    
  session_id (string, required)
    Unique session identifier (maintains conversation context)
    
  wallet_address (string, required)
    User's connected Privy wallet address
    
  enable_swap_execution (boolean, optional)
    Set to true to allow AI to generate transactions
    Default: false for read-only mode


Response Payload:

  reply (string)
    Text response from AI agent with transaction details or errors
    
  userid (string)
    Echo of request userid
    
  session_id (string)
    Echo of request session_id
    
  data (object)
    Optional object containing execution data
    
    swap_execution (object, optional)
      Present when AI generated a swap transaction
      
      quote (object)
        inputAmount (string): Amount of input token in wei
        outputAmount (string): Expected amount of output token
        priceImpact (string): Price impact percentage
        minOut (string): Minimum output (slippage protection)
        
      transaction (object)
        to (string): Router contract address
        data (string): ABI-encoded function call
        from (string): User wallet address
        gasLimit (string): Calculated gas limit
        value (string): "0" for token swaps

SWAP FLOW EXAMPLE:

User Request: "Swap 1 USDC to EURC"

Step 1: AI Agent receives message
  Parses intent: inputToken=USDC, outputToken=EURC, inputAmount=1
  Resolves: 1 USDC = 1,000,000 wei

Step 2: Backend generates quote
  Calls RouteOptimizer for best DEX path
  Calculates: 1 USDC → ~1.05 EURC (example rate)
  Applies slippage: minimum output = 1.04 EURC

Step 3: Backend builds transaction
  Encodes swap function call
  Sets router contract as recipient (to)
  Includes encoded data with swap parameters

Step 4: Returns transaction to frontend
  Includes full transaction object with to, data, value, from, gasLimit

Step 5: User signs with Privy wallet
  Wallet popup appears
  User reviews transaction
  User clicks confirm to sign

Step 6: Frontend broadcasts transaction
  Sends eth_sendTransaction with signed data
  Privy wallet returns transaction hash

Step 7: Frontend confirms on-chain
  Polls Arc RPC every 1 second
  Checks eth_getTransactionReceipt
  Transaction confirmed in block

Step 8: Confirmation recorded
  Sends POST to /api/ai/confirm-transaction
  Stores in Supabase transaction_confirmations table


PAYMENT FLOWS SUPPORTED:

Direct Token-to-Token Swaps
  USDC → EURC
  EURC → QTM
  Any token → any token
  Single transaction, no intermediate steps

Multi-hop Swaps (when optimal)
  USDC → QPair → QTM (best rate)
  Backend automatically routes through multiple pools
  Single transaction from user perspective

Slippage Protection
  Backend calculates minimum output
  Set in transaction before signing
  Protects user from price impact

Gas Included
  Backend includes optimal gas estimate
  User pays gas cost + swap fee
  No additional transaction needed


TOKEN APPROVAL HANDLING:

First-time swap for new token:
  User may need to approve token spending
  Backend checks if approval needed
  Frontend displays approval step if required
  User signs approval transaction first
  Then signs actual swap transaction

Subsequent swaps:
  Token already approved
  No additional approval needed
  Direct swap transaction only

PART 6: INDEXING, ANALYTICS & DATA QUERYING
================================================================================

Supabase PostgreSQL Database and Analytics

All transactions and conversation history stored in Supabase for audit trail
and analytics.

DATABASE SCHEMA:

transaction_confirmations Table

  Columns:
    id (UUID primary key)
    wallet_address (varchar)
    session_id (varchar)
    transaction_hash (varchar)
    block_number (integer)
    status (varchar) - "success" or "failed"
    gas_used (varchar)
    created_at (timestamp)
    
  Constraints:
    - Immutable: No updates/deletes allowed after creation
    - Row-Level Security: Users see only their own transactions
    - Indexes on wallet_address and transaction_hash

ai_db Table (Chat History)

  Columns:
    id (UUID primary key)
    wallet_address (varchar)
    session_id (varchar)
    user_query (text)
    ai_response (text)
    created_at (timestamp)


QUERY EXAMPLES:

Get User Transaction History:

SELECT 
  transaction_hash,
  status,
  block_number,
  gas_used,
  created_at
FROM transaction_confirmations
WHERE wallet_address = '0x57d4721c604635df57d9c33e7b0b0f5c5da27a67'
ORDER BY created_at DESC
LIMIT 50;

Calculate Success Rate:

SELECT 
  COUNT(*) as total_transactions,
  COUNT(CASE WHEN status = 'success' THEN 1 END) as successful,
  ROUND(100.0 * COUNT(CASE WHEN status = 'success' THEN 1 END) / 
    COUNT(*), 2) as success_rate_percent
FROM transaction_confirmations
WHERE created_at > NOW() - INTERVAL '24 hours';

Analyze Gas Costs:

SELECT 
  AVG(CAST(gas_used AS NUMERIC)) as average_gas,
  SUM(CAST(gas_used AS NUMERIC)) as total_gas_consumed,
  COUNT(*) as transaction_count,
  DATE_TRUNC('hour', created_at) as hour
FROM transaction_confirmations
GROUP BY DATE_TRUNC('hour', created_at)
ORDER BY hour DESC;

Top Users by Activity:

SELECT 
  wallet_address,
  COUNT(*) as swap_count,
  MAX(created_at) as last_transaction,
  COUNT(CASE WHEN status = 'success' THEN 1 END) as successful_swaps
FROM transaction_confirmations
GROUP BY wallet_address
ORDER BY swap_count DESC
LIMIT 20;

Join Chat History with Transactions:

SELECT 
  ai.user_query,
  ai.ai_response,
  tc.transaction_hash,
  tc.status,
  tc.block_number,
  tc.created_at
FROM ai_db ai
LEFT JOIN transaction_confirmations tc
  ON ai.session_id = tc.session_id
WHERE ai.wallet_address = '0x57d4721...'
ORDER BY ai.created_at DESC;

Step 1: Get transaction from API
  response = await fetch(`${API_ENDPOINT}/api/v1/chat`, {

  receipt = null;

    receipt = await pollRPC('eth_getTransactionReceipt', [txHash]);
    if (receipt) break;
    await sleep(1000);
  }

  await fetch(`${API_ENDPOINT}/api/ai/confirm-transaction`, {

      session_id: sessionId,

================================================================================
TROUBLESHOOTING
================================================================================

Wallet Popup Not Appearing

Issue: AI returns swap message, but no wallet popup
Solution:
  1. Check browser console for errors
  2. Verify Privy app ID is correct in environment variables
  3. Ensure user is logged in (check usePrivy hook)
  4. Confirm response.data.swap_execution is present (check network tab)
  5. Check browser permissions for wallet popups

Transaction Fails to Confirm

Issue: Wallet signs transaction, but confirmation never arrives
Solution:
  1. Check Arc RPC endpoint is accessible
  2. Verify transaction hash is correct format (0x...)
  3. Check Arc scanner to see if transaction was included
  4. If in mempool, try re-broadcasting
  5. Check gas limit isn't too low

Database Queries Slow

Issue: Supabase queries returning slowly
Solution:
  1. Check if wallet_address index exists
  2. Limit query results with LIMIT clause
  3. Use materialized views for analytics
  4. Enable query caching
  5. Check database CPU/memory usage

AI Agent Not Responding

Issue: /api/v1/chat endpoint hangs or times out
Solution:
  1. Check Railway backend is running
  2. Verify environment variables set in Railway
  3. Check OpenAI API key is valid
  4. Look at Railway logs for errors
  5. Try restarting container
