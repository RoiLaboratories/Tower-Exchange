TOWER EXCHANGE
HOW THE APP WORKS

Tower Exchange is a wallet-connected trading application built around testnet crypto workflows. The app combines direct trading, cross-chain bridging, AI-assisted trading, recurring orders, portfolio-style views, and wallet-linked activity tracking in one interface.

At a high level, the app works like this:

The user opens the app and can browse the interface immediately, but most meaningful actions require a connected wallet.

Once the wallet is connected, the wallet address becomes the user's main identity inside the app. That address is used to load balances, save activity history, save chat history, save recurring orders, and associate profile information with the user.

The app has five main product behaviors:

Trading
Bridging
AI chat and AI-assisted actions
Recurring orders
Profile and history tracking

GENERAL USER FLOW

When the app loads, it shows a shared header, footer, and a wallet connection layer.

After connection, the user can move between the main experiences:

The home trading screen
The dedicated bridge screen
The AI agent screen
The recurring orders screen
The profile screen

The app keeps the experience very stateful in the browser. It stores things like chat sessions, some profile data, and recurring-order cache locally so the interface feels continuous even before remote data is reloaded.

WALLET AND IDENTITY FLOW

Wallet connection is handled through Privy.

Privy gives the app access to the user's wallet session and address. That address is then reused everywhere as the core user key.

The wallet is used for three different jobs:

Identity
The address identifies the user in history, chat, and recurring-order records.

Authorization
The app only allows swaps, bridges, and other transaction-driven actions when the wallet is connected.

Signing
When the user confirms a swap, the browser wallet signs and submits the transaction.

TRADING FLOW

The trading experience is centered around token swaps on Arc Testnet.

The swap flow works in this order:

The user selects input token, output token, and amount.
The frontend requests a quote from the external swap backend.
The backend returns route and transaction-building data.
The frontend requests the final swap transaction payload from the backend.
If approval is required, the app prepares that first.
The user signs the transaction through the connected wallet.
The app submits the transaction and then polls the Arc network until confirmation is found.
After confirmation, the app records the result and can trigger post-swap fee handling.

From the user's point of view, the trading screen is doing three things at once:

Showing live quote and routing information
Preparing the correct transaction payload
Tracking the transaction after the wallet submits it

AI CHAT FLOW

The AI screen is not just a chatbot. It is a combined workspace that lets the user talk to the AI while also opening recurring buy, recurring sell, and portfolio analysis tools from the same page.

The AI side works like this:

The user sends a message.
The app sends the message to the external AI backend through an internal proxy route.
The AI backend returns a normal text reply or a structured action payload.
The app shows the assistant's reply and stores the conversation history.

The AI can respond in different modes:

Plain conversational reply
Wallet-aware reply
Portfolio-aware reply
Swap-aware reply

If the AI decides that the user asked for a swap, the reply can include transaction details. In that case the frontend treats the AI response as an executable workflow:

The AI supplies swap execution data.
The app shows the response in chat.
The app opens transaction confirmation UI.
The wallet signs and sends the transaction.
The app waits for blockchain confirmation.
The app then logs the confirmed result and informs the AI backend that the action completed.

So the AI screen is effectively a command interface sitting on top of trading and portfolio functions.

CHAT SESSION BEHAVIOR

Chat sessions are managed as named conversations.

The app keeps a local list of sessions in the browser so the user can quickly switch between conversations.
It also loads and saves chat history remotely so the conversation is not purely local.

When a session is opened, the app rebuilds the visible message list from stored history.
When a new message is sent, the session metadata is updated so the conversation title and message count stay current.

BRIDGE FLOW

The bridge experience is focused on moving USDC between supported test networks.

The bridge screen lets the user choose:

Source chain
Destination chain
Amount
Receiving address

The app validates the route and receiving address before execution.
It calculates an estimated bridge fee and estimated completion time.
It then attempts to execute the bridge using the Circle bridge stack.

From the user's point of view, bridging is a guided transfer flow:

Choose the chain to send from
Choose the chain to receive on
Enter amount
Confirm destination
Execute
Wait for cross-chain completion

The bridge screen also reads balances from the selected source and destination networks so the user can see what they have before and after bridging.

RECURRING ORDER FLOW

Recurring orders let the user schedule repeated buy or sell actions.

The user creates either a recurring buy or recurring sell order by choosing:

Order type
Source token
Target token
Amount
Frequency
Optional end date

When the order is created, the app stores it remotely and updates the recurring orders dashboard.

The recurring orders dashboard gives the user a live management view:

View active orders
View execution history
Cancel orders
Inspect past executions

Recurring orders are not only UI records. They are intended to be executed automatically in the background.

The intended recurring execution loop is:

Store an active order with a next execution time
Background job checks which orders are due
For each due order, request a quote and attempt execution
Log the execution result
Move the next execution time forward

So recurring orders turn one manual trading decision into an ongoing automated schedule.

PROFILE AND ACTIVITY FLOW

The profile area is the user's personal record inside the app.

It is tied to the wallet address and is used for two main things:

Profile image handling
Activity history

Profile image behavior:

The user uploads an image.
The image is stored remotely.
The app caches the resulting public image URL locally.
The image is then reused across chat and profile surfaces.

Activity behavior:

Swaps, bridges, and recurring-order actions can be written into the activity history.
The profile experience reads that history and shows what the user has done over time.

This gives the app continuity beyond the current session. The user is not only trading in the moment; the app also builds a usable record of actions.

DATA MOVEMENT INSIDE THE APP

The app works by moving data through a few connected layers:

Browser UI layer
This is where the user interacts with forms, buttons, chat, tabs, and modals.

Wallet layer
This is where transaction approval and signing happen.

Application server routes
These routes proxy certain requests so secrets and backend credentials are not exposed directly to the browser in some flows.

External service layer
This includes the AI backend, the swap backend, blockchain RPC endpoints, and bridge services.

Persistence layer
This stores history, recurring orders, confirmations, and profile assets.

The result is that the app is not monolithic. It behaves more like an orchestrator:

The UI gathers intent from the user.
The wallet authorizes transactions.
External services generate quotes, actions, or route information.
The app records the outcome for future use.

WHAT HAPPENS AFTER A TRANSACTION

After a transaction is signed and sent, the app does not stop at wallet submission.

It continues into a post-transaction phase:

Wait for chain confirmation
Display confirmation or failure state
Save relevant result data
Update user-facing history
Inform dependent systems if needed

This is especially important in AI-assisted swaps, where the chat experience needs to know whether the blockchain action really finished.

HOW THE APP KEEPS STATE

The app keeps state in two places:

Local browser state
Used for session continuity, fast UI updates, local chat session tracking, cached profile data, and some recurring-order fallback storage.

Remote stored state
Used for chat history, transaction confirmations, activity history, recurring orders, recurring executions, and profile assets.

This dual approach makes the app feel responsive while still preserving history across visits.

HOW THE DIFFERENT PARTS FIT TOGETHER

The best way to think about the app is as three connected systems sharing one wallet identity:

Execution system
Handles swaps and bridges.

Intelligence system
Handles AI chat, portfolio-style questions, and AI-triggered actions.

Persistence system
Handles history, recurring orders, profile state, and confirmations.

These systems are joined by the same wallet address and the same testnet environment.

PRACTICAL PRODUCT MODEL

In practical terms, this is what the app is doing for the user:

It lets the user connect a wallet.
It lets the user trade and bridge testnet assets.
It lets the user talk to an AI that can understand wallet-related context.
It lets the user create automated recurring buy and sell plans.
It tracks what the user has done so that trading, chat, and profile history are not isolated from each other.

CURRENT OPERATING CHARACTERISTICS

The app is strongly centered on Arc Testnet.

The app depends on external backend services for AI responses and swap-building logic.

The AI feature is not only informational. It can trigger actionable blockchain workflows when the response includes execution payloads.

Recurring orders are designed as a background automation feature rather than just a front-end list of plans.

The same wallet identity ties together execution, history, profile state, and AI context.

SUMMARY

Tower Exchange works as a wallet-connected trading workspace. The user connects a wallet, trades or bridges assets, talks to an AI assistant that can help interpret or execute trading intent, sets up recurring orders for repeat behavior, and sees a history of those actions in a profile-linked system. The app itself acts as the coordinator between the user interface, the wallet, external AI and swap services, blockchain networks, and stored history.
